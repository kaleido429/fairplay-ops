# Optical Flow를 CPU에서 GPU로 바꿔도 되는가: 검증 결과

작성일: 2026-11-27

## 결론

- GPU(CUDA) Farneback은 CPU보다 디코딩 포함 5.9배 빠르다.
- 계산값이 미세하게 달라서 87개 영상 중 판정이 바뀌는 영상이 있다(윈도우 최댓값 규칙 6개, 영상 평균 규칙 1개).
- 따라서 지금 모델과 임계값에 GPU 결과를 그대로 넣으면 안 된다. GPU를 쓰려면 학습용 영상 255개도 GPU로 다시 추출해 모델과 임계값을 새로 정해야 한다.
- 실제로 재학습해 보니 교차검증 성능은 CPU와 같았다(아래 "GPU 데이터로 재학습한 결과"). 학습과 판정을 모두 GPU 데이터로 하면 GPU로 바꿔도 된다.
- 정상 영상의 판정(오탐)은 두 규칙 모두 하나도 바뀌지 않았다.

## 무엇을 비교했나

아래에서 `reeval`은 원래 저장소 [Fairplay-Fairy](https://github.com/kaleido429/Fairplay-Fairy)의 재평가 폴더를 가리킨다. 판정 규칙은 두 가지다. 윈도우 최댓값 규칙은 영상의 윈도우 확률 중 최댓값이 임계값을 넘으면 치트로 판정하고, 영상 평균 규칙은 윈도우 확률의 평균이 임계값을 넘으면 치트로 판정한다.

- 대상: 홀드아웃 영상 91개(치트 43, 정상 48). 학습과 임계값 결정에 쓰지 않은 영상.
- 방법: 같은 프레임 쌍에 대해 CPU와 GPU로 각각 Optical Flow를 계산하고, 이후 단계(프레임 특징 → 윈도우 특징 105개 → XGBoost 확률 → 영상 판정)를 똑같이 적용.
- CPU: `cv2.calcOpticalFlowFarneback(prev, roi, None, 0.5, 3, 15, 3, 5, 1.2, 0)`
- GPU: `cv2.cuda.FarnebackOpticalFlow`, 같은 파라미터(numLevels 3, pyrScale 0.5, winSize 15, numIters 3, polyN 5, polySigma 1.2)
- 전처리는 `reeval/extract_aim.py`와 동일(시작 3초 제외, 화면 중앙 60% 영역).
- 모델과 임계값은 `reeval/holdout_eval.py`와 같은 절차(원본 255개 영상의 5-fold 결과로 임계값 결정, 전체로 학습).
- 환경: OpenCV 4.12.0을 CUDA 12.4로 직접 빌드, Python 3.12, 6개 프로세스 병렬 실행.

해석:

- 윈도우 최댓값 규칙은 임계값이 0.99981이고 바뀐 영상의 점수가 0.99970~0.99991에 몰려 있다. 소수 넷째 자리 차이로 판정이 뒤집힌다. GPU의 문제라기보다 이 규칙이 작은 수치 변화에 약하다는 뜻이다.
- GPU 쪽 적발이 2개 많게 나온 것은 개선이 아니라 경계 근처 영상이 우연히 넘어간 결과다.
- 영상 점수의 최대 차이: 평균 확률 0.13, 최댓값 확률 0.30.

### 왜 값이 다른가

- CPU 구현과 GPU 구현은 서로 다른 코드다. 연산 순서가 다르면 부동소수점 반올림 결과가 달라진다.
- Farneback은 피라미드 3단계 × 반복 3회로 이전 결과를 다음 계산에 넣는다. 작은 차이가 단계를 거치며 커진다.

### CPU끼리도 완전히 같지는 않다

기존 추출(OpenCV 5.1.0)과 새 빌드(4.12.0)의 CPU 결과를 비교하면 프레임의 약 52%만 값이 완전히 같았다. 차이는 평균 0.0004, 상위 1% 0.008, 최대 0.35 px/frame로 GPU 차이보다 훨씬 작고, 87개 영상 모두 두 규칙에서 판정이 같았다(평균 확률 최대 차이 0.003). 다만 윈도우 최댓값 규칙처럼 경계가 좁으면 라이브러리 버전만 바뀌어도 판정이 뒤집힐 수 있다.

## GPU 데이터로 재학습한 결과 (2026-11-27 추가)

학습용 영상 256개를 Firebase Storage에서 받아 GPU로 다시 추출하고, 기존 평가 스크립트(`reeval.py`, `holdout_eval.py`)를 수정 없이 GPU 데이터에 적용했다. 하이퍼파라미터와 절차는 그대로다.

- 학습 데이터: 기존 엑셀과 같은 영상 255개, 윈도우 5,569개(기존과 개수·위치 일치). Storage의 256개 중 1개(videos/b4aa5670-…)는 기존 엑셀에 없어 제외.
- 홀드아웃: 91개 전부. 프레임 크기가 바뀌는 영상 6개는 첫 프레임 크기로 맞춘 뒤 계산(위에서 실패했던 4개 포함).

### 교차검증 (5-fold × 10회, 치트 25 / 정상 230)

| 판정 규칙 | CPU 재현율 | GPU 재현율 | CPU 오탐률 | GPU 오탐률 |
|---|---|---|---|---|
| 윈도우 최댓값 | 0.59 (11~21개) | 0.58 (10~20개) | 0.61% | 0.65% |
| 영상 평균 | 0.76 (16~21개) | 0.77 (16~20개) | 0.26% | 0.35% |
| 참고: 평균 > 0.5 | 0.87 | 0.89 | 0.96% | 0.87% |

영상 단위 ROC-AUC: CPU 0.994 / 0.997, GPU 0.993 / 0.997 (최댓값 집계 / 평균 집계).

교차검증 기준으로 CPU와 GPU의 성능은 같다.

### 홀드아웃 (치트 43 / 정상 48)

| 판정 규칙 | CPU 임계값 | GPU 임계값 | CPU 적발 | GPU 적발 | CPU 오탐 | GPU 오탐 |
|---|---|---|---|---|---|---|
| 윈도우 최댓값 | 0.99981 | 0.99972 | 25/43 | 35/43 | 0/48 | 0/48 |
| 영상 평균 | 0.628 | 0.576 | 34/43 | 38/43 | 4/48 | 4/48 |
| 참고: 평균 > 0.5 | - | - | 42/43 | 40/43 | 4/48 | 4/48 |

ROC-AUC: CPU 0.996 / 0.938, GPU 0.994 / 0.940.

- 정상 영상 판정은 CPU와 GPU가 완전히 같다. 오탐 4건도 같은 영상이다.
- 적발 수는 GPU 쪽이 많다(윈도우 최댓값 규칙 +10, 영상 평균 규칙 +4). 그러나 이것을 "GPU가 더 잘 잡는다"로 해석하면 안 된다.
  - ROC-AUC와 교차검증 수치가 같다. 모델의 구분 능력은 달라지지 않았다.
  - 차이는 임계값에서 나왔다. 임계값은 "학습 데이터의 정상 영상 중 점수가 가장 높은 영상 1개"로 정해지는데, 그 영상의 점수가 GPU 데이터에서 조금 낮게 나와 임계값이 내려갔다. 영상 1개에 좌우되는 값이라 우연의 영향이 크다.
  - 임계값을 고정한 "평균 > 0.5" 규칙에서는 오히려 GPU가 2개 적다(42 → 40).
  - 홀드아웃을 이미 한 번 본 뒤에 다시 쓴 평가이므로, 처음 1회 적용한 CPU 결과만큼의 증거 가치는 없다.

### 추출 시간 (GPU, 6개 프로세스, 디코딩 포함)

| 대상 | 영상 | 프레임 | 걸린 시간 |
|---|---|---|---|
| 학습용 | 256개 | 203,718 | 772초 (약 13분) |
| 홀드아웃 | 91개 | 69,582 | 279초 (약 5분) |

같은 조건의 CPU 추출 시간은 따로 재지 않았다. 위 비교 실행의 CPU 흐름 계산 시간(87개 영상 합계 17,608초)을 6개 프로세스로 나누면 약 50분이다.

### 판단

- GPU로 추출하고 GPU 데이터로 재학습하면 성능은 CPU와 같고 추출은 훨씬 빠르다. 파이프라인을 GPU로 바꿔도 된다.
- 조건: 학습과 판정에 같은 방식으로 추출한 데이터를 써야 한다. CPU로 학습한 모델에 GPU 데이터를 넣는 혼용은 안 된다.
- 보고 수치는 처음 1회 적용한 CPU 홀드아웃 결과(25/43, 34/43, 오탐 4/48)를 기준으로 둔다.
- 임계값이 정상 영상 1개에 좌우되는 문제가 이번에 드러났다. 임계값 결정 방법(예: 반복 교차검증의 평균, 상위 분위수)을 따로 검토할 필요가 있다.

파일(`../gpu_compare/`): `extract_aim_gpu.py`, `make_windows.py`, 결과 요약 `reeval_gpu_summary.json`, `hold_gpu_summary.json`. 추출값 CSV와 윈도우 특징 엑셀은 용량이 커서 저장소에 넣지 않았다. 영상 원본도 저장소에 없다.

## 앞으로

- 보고한 성능 수치는 CPU(OpenCV 5.1.0) 기준을 유지한다.
- GPU를 쓰려면: 학습용 255개를 GPU로 재추출 → 모델 재학습 → 임계값 재결정 → 홀드아웃 재평가. 추출 환경(CPU/GPU, OpenCV 버전)을 결과와 함께 기록한다.
- 윈도우 최댓값 규칙은 임계값 경계가 지나치게 좁다. 판정 보류 구간을 두거나 평균 기준 규칙을 쓰는 편이 안정적이다. (이후 전체 영상 교차검증에서는 영상 평균 규칙이 더 불안정했다. `전체_교차검증.md` 참고.)
- 프레임 크기가 바뀌는 영상은 추출 단계에서 크기를 맞추거나 명시적으로 제외하고 기록해야 한다.

## 재현 방법

파일 위치: `../gpu_compare/`

```
python compare_flow.py <영상 루트> all.csv 6        # CUDA 빌드 OpenCV 필요, all.csv와 all_time.csv 생성
python compare_eval.py <reeval 폴더> all.csv        # 차이·판정 비교, all_videos.csv 생성
```

- `all.csv`: 프레임별 dx, dy (CPU, GPU)와 픽셀 차이 (11MB, 저장소 미포함)
- `all_time.csv`: 영상별 디코딩, CPU, GPU 시간
- `all_videos.csv`: 영상별 점수 (CPU, GPU)
- OpenCV 빌드 설정: `../opencv_build/configure.bat`, `build.bat`
