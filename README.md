# Fairplay Fairy 후속 작업 정리

졸업작품 Fairplay Fairy(게임 플레이 영상으로 에임봇을 탐지하는 모델)의 영상 처리와 판정 과정을 GPU와 SQL 기반 파이프라인으로 다시 만들고, 그 과정에서 확인한 결과를 정리한 문서.

- 기간: 2026-11-26 ~ 2026-11-28
- 원래 저장소([Fairplay-Fairy](https://github.com/kaleido429/Fairplay-Fairy))는 수정하지 않았다. 이 폴더의 코드와 결과는 모두 별도 작업이다.
- 특징 105개의 정의와 XGBoost 하이퍼파라미터는 졸업작품 팀의 기존 모델을 그대로 가져왔다. 이 작업에서 새로 한 것은 추출 방식(GPU), 저장과 분석(SQL), 평가 절차다.

## 1. 전체 흐름

```
영상(.webm) 347개
   │  ① GPU Optical Flow (OpenCV CUDA, Farneback)      Python
   ▼
frames 테이블: 프레임별 조준 이동량 (dx, dy) 273,300행      SQLite
   │  ② 150프레임 윈도우 특징 105개 → XGBoost 확률       Python
   ▼
windows 테이블: 윈도우별 치트 확률 7,466행                 SQLite
   │  ③ 영상 점수, 임계값 비교, 판정, 성능, 오탐 분석      SQL
   ▼
판정 결과와 분석 표
```

한 명령으로 처음부터 끝까지 실행된다.

```
python pipeline/run_pipeline.py --db fairplay.db --train <학습 영상 폴더> --holdout <홀드아웃 영상 폴더>
```

DB는 SQLite를 썼다. 서버 설치 없이 파일 하나로 동작하고, 윈도우 함수와 CTE 등 표준 SQL 문법을 그대로 쓸 수 있다. MS SQL Server 같은 서버형 DB는 쓰지 않았다.

## 2. 진행 순서와 결과

### 2.1 OpenCV를 CUDA로 빌드

pip로 설치하는 OpenCV에는 GPU 기능이 없다. OpenCV 4.12.0을 CUDA 12.4로 직접 빌드했다(설정은 `opencv_build/`). Python에서는 `cv2.cuda.FarnebackOpticalFlow`를 쓴다.

### 2.2 CPU와 GPU의 결과가 같은지 검증

속도만 보고 바꾸지 않고, 같은 영상에 두 방식을 적용해 값을 비교했다(홀드아웃 87개).

| 항목 | 결과 |
|---|---|
| 속도 | 디코딩 포함 5.9배, 흐름 계산만 7.4배 빠름 |
| 프레임 평균 이동량 차이 | 중앙값 0.0039 px (상대 차이 0.24%) |
| 차이가 큰 특징 | 각도 계열. 거의 안 움직이는 프레임에서 작은 차이에도 각도가 크게 바뀜 |
| 윈도우 확률 차이 | 평균 0.022, 최대 0.62 |
| 판정이 바뀐 영상 | 윈도우 최댓값 규칙 6개, 영상 평균 규칙 1개. 정상 영상은 0개 |

결론: CPU로 학습한 모델에 GPU 추출값을 넣으면 안 된다. 학습과 판정에 같은 방식으로 추출한 데이터를 써야 한다.

부수적으로 확인한 것: CPU끼리도 OpenCV 버전(5.1.0과 4.12.0)이 다르면 프레임의 약 52%만 값이 완전히 같다. 재생 중 프레임 크기가 바뀌는 영상 6개는 첫 프레임 크기로 맞춰 처리했다.

### 2.3 GPU 데이터로 재학습

학습용 영상 256개를 GPU로 다시 추출해 같은 절차로 학습하고 평가했다.

| 판정 규칙 | CPU 재현율 | GPU 재현율 | CPU 오탐률 | GPU 오탐률 |
|---|---|---|---|---|
| 윈도우 최댓값 | 0.59 | 0.58 | 0.61% | 0.65% |
| 영상 평균 | 0.76 | 0.77 | 0.26% | 0.35% |

(영상 255개, 5-fold × 10회 교차검증) 성능은 같다. 추출 시간은 347개 전체가 약 28분이다.

### 2.4 임계값이 불안정하다는 것을 발견

GPU 재학습 후 홀드아웃 적발이 25개에서 35개로 늘었는데, 교차검증 성능은 그대로였다. 원인을 찾아보니 추출 방식이 아니라 임계값이었다.

- 임계값은 "학습 데이터의 정상 영상 중 최고 점수 1개"로 정한다.
- 교차검증 분할 시드만 바꿔도 이 값이 달라진다. 홀드아웃 적발 수가 윈도우 최댓값 규칙 18~42개, 영상 평균 규칙 20~36개(43개 중)까지 움직였다.
- 대책: 분할을 20번 바꿔 얻은 영상 점수를 평균한 뒤 최고 점수를 임계값으로 쓴다. CPU와 GPU의 임계값이 거의 같아진다(0.99968 / 0.99969).
- 근본 원인은 정상 학습 영상이 230개뿐이라는 것이다.

### 2.5 SQL 파이프라인

추출값을 CSV와 엑셀로 주고받던 것을 SQLite로 옮겼다.

| 테이블 | 한 행의 의미 | 행 수 |
|---|---|---|
| `videos` | 영상 1개. 해상도, FPS, 추출 방식, 상태 | 347 |
| `frames` | 프레임 1개의 조준 이동량 | 273,300 |
| `windows` | 150프레임 윈도우 1개의 치트 확률 | 7,466 |
| `thresholds` | 판정 규칙과 방식별 임계값 | 4 |
| `runs` | 단계별 실행 기록 | - |

| 뷰 | 내용 | 쓰인 SQL |
|---|---|---|
| `frame_features` | 프레임별 속도, 가속도, 저크, 각도 변화 | `LAG` 윈도우 함수, CTE |
| `video_scores` | 영상별 윈도우 확률의 최댓값과 평균 | `JOIN`, `GROUP BY` |
| `verdicts` | 점수와 임계값을 비교한 판정 | `CROSS JOIN`, `CASE` |
| `video_activity` | 영상별 평균 속도와 정지 프레임 비율 | 뷰 위의 집계 |

| 쿼리 | 내용 | 쓰인 SQL |
|---|---|---|
| `01_dataset` | 구분별 영상 수와 프레임 수 | `GROUP BY`, 조건부 `SUM` |
| `02_performance` | 규칙별 적발, 오탐, 재현율, 오탐률 | 뷰 집계 |
| `03_false_positives` | 오탐 영상의 활동량과 순위 | `JOIN` 3개, `PERCENT_RANK` |
| `04_activity_groups` | 활동량 4분위별 오탐률 | `WITH`, `NTILE(4)` |
| `05_resolution` | 해상도별 분포와 판정 | `GROUP BY` 두 열 |
| `06_threshold_check` | 임계값 검산 | 서브쿼리, `CROSS JOIN` |

역할 분담: 프레임 특징과 집계, 판정, 분석은 SQL. 영상 디코딩과 Optical Flow, 윈도우 통계 105개(왜도, 첨도, 엔트로피 등), 모델 학습은 Python.

실행: 347개 영상 전체 1,875초(GPU 추출 1,708초, 특징·학습·임계값 163초). 실패 0개. extract 단계는 영상 단위 트랜잭션으로 저장해 중간에 끊겨도 이어서 실행된다.

검산:

- `frames`의 값이 별도 스크립트로 추출한 GPU 결과와 완전히 일치.
- SQL로 계산한 프레임 특징과 Python 계산의 차이 1e-13 이하.
- SQL로 구한 임계값과 Python이 저장한 임계값 일치.

SQL로 확인한 것:

- 홀드아웃 오탐 4건이 모두 평균 속도 하위 25% 영상이다. 이 구간의 오탐률은 4/12, 나머지 구간은 0/36이다. 3건은 정지 프레임 비율이 약 50%다.
- 홀드아웃 치트 영상 43개는 모두 1920×1080(2개는 1920×1079)이고, 정상 영상은 1280×720부터 3840×2160까지 퍼져 있다. 녹화 환경 편향이 있다.

### 2.6 전체 영상 교차검증

치트 영상 68개 중 학습에 25개만 쓰고 있었다. 홀드아웃은 이미 여러 번 확인해 최종 시험으로서의 의미가 줄었으므로, 346개 전체(치트 68, 정상 278)를 합쳐 중첩 교차검증했다. 임계값은 학습 폴드 안에서만 정했다.

| 판정 규칙 | 임계값 방식 | 적발 (68개 중) | 재현율 | 오탐 (278개 중) | 오탐률 |
|---|---|---|---|---|---|
| 윈도우 최댓값 | 10회 평균 | 60.0 (59~61) | 0.88 | 2.8 (2~4) | 1.0% |
| 윈도우 최댓값 | 분할 1회 | 56.2 (54~59) | 0.83 | 1.4 (0~3) | 0.5% |
| 영상 평균 | 10회 평균 | 38.0 (35~45) | 0.56 | 1.0 (0~2) | 0.4% |
| 영상 평균 | 분할 1회 | 29.8 (21~40) | 0.44 | 0.6 (0~1) | 0.2% |

(바깥 분할 시드 5개의 평균, 괄호는 최소~최대. 영상 단위 ROC-AUC 0.993~0.997)

- 학습 데이터를 늘린 효과가 있다. 기존 학습용 치트 25개의 적발률이 0.59에서 0.70~0.80으로 올랐다.
- 영상 평균 규칙은 재현율이 크게 떨어졌다. 저활동 정상 영상 1개(평균 확률 0.94)가 학습에 들어오면서 임계값이 0.6대에서 0.93으로 올랐기 때문이다.
- 영상 255개 기준으로는 영상 평균 규칙이 더 나았지만, 데이터를 늘리자 뒤집혔다. 두 규칙 모두 영상 순위는 잘 매기고(AUC 0.99 이상), 차이는 임계값을 정상 영상 최고 점수 하나로 정하는 방식에서 나온다.

## 3. 정리

| 한 일 | 결과 |
|---|---|
| Optical Flow를 GPU로 전환 | 5.9배 빠름. 값이 미세하게 달라 재학습이 필요함을 확인하고 재학습 |
| 임계값 결정 방식 점검 | 분할 시드에 따라 홀드아웃 적발이 18~42개로 흔들림을 발견. 평균 방식으로 안정화 |
| 저장과 분석을 SQL로 이전 | 테이블 5개, 뷰 4개, 분석 쿼리 6개. 영상 폴더에서 판정까지 한 명령 |
| 전체 데이터 교차검증 | 재현율 0.88, 오탐률 1.0% (윈도우 최댓값 규칙, 평균 임계값) |

## 4. 한계

1. 최종 시험용 데이터가 없다. 홀드아웃을 여러 번 확인했고 2.6에서는 학습에도 썼다. 위 수치는 현재 데이터 안에서의 성능이며, 새 환경에서의 성능은 새로 수집한 영상으로 확인해야 한다.
2. 촬영자 정보가 없어 영상 단위로만 나눴다. 같은 환경에서 찍은 영상이 학습과 평가에 함께 들어가 수치가 낙관적일 수 있다.
3. 치트 영상과 정상 영상의 녹화 환경이 다르다(2.5). 모델이 치트가 아니라 환경을 구분했을 가능성을 배제하지 못했다.
4. 거의 움직이지 않은 정상 영상을 치트로 판정한다. 활동량이 낮은 영상은 판정을 보류하는 단계가 필요하다.
5. 에임봇 1종, 설정 1종만 다뤘다.
6. 특징 단위가 px/frame이라 해상도와 프레임레이트의 영향을 받는다.
